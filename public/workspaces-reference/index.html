⚠️ Critical: Why We Have Two Workspaces
Third Play operates a dual-workspace architecture in Demandbase (Tenant 15053). This was NOT by design — it resulted from the Fraud Campaign incident on April 26, 2025. A globally-scoped advertising campaign accidentally targeted 4.8M contacts in Germany and MENA regions, violating data governance rules. The Global Workspace was created to isolate US targeting from international regions. The dual-workspace setup is a permanent governance control, not a temporary workaround.

Journey Stages

Journey Stage Alignment — "US Journey" Mapping

Journey stages built in Admin → Journey Stages do not appear in campaign and list selectors on their own. The stage values translate from the Admin journey definition into the [US Journey] object, and every advertising list must be mapped to US Journey for the US Workspace to read them. Until that mapping is in place, the Journey Stage selector returns 0 selected values.

The Translation Rule — Match US Journey Everywhere
Once stages live in Admin → Journey Stages, you must map US Journey to everything downstream — or the US Workspace will not read it.

• Advertising lists: set the Journey Stage selector to [US Journey] and select the stage values.
• Campaign setup: the campaign's journey stage must match the Admin US Journey definition, not a separate/legacy journey.
• Consistency: if any list points to a different journey, its stages won't translate and the selector shows 0 selected values.
Troubleshooting — Selector Shows "0 Selected Values"
1. Confirm the stages exist and are saved/published in Admin → Journey Stages (not draft).
2. Confirm the list/campaign is filtering on [US Journey] — the journey that carries the Admin stages.
3. Confirm US Journey is the default funnel mapped for the US Workspace.
4. Hard-refresh the selector (the picklist caches per session). Newly mapped stages populate once accounts are assigned to them.
Non-Negotiable

7 TP Rules

These rules govern all Demandbase platform operations for Third Play USA. Non-compliance risks data leakage, attribution failures, and advertising errors. These are platform constraints, not best practices — they cannot be bypassed.

1

Every account list and person list lives in both workspaces. Build it in US, then duplicate it to Global with a [US] prefix.

2

Advertising campaigns only read from Global. A list in US Workspace alone will not populate an ad audience.

3

Geo is set to United States explicitly. "North America" includes Mexico by default.

4

Every advertising campaign includes a Person List under Known Contacts.

5

Person lists are Dynamic, built in Advanced selector mode.

6

Keyword management is admin-gated. All keyword additions route through Sharath.

7

SFDC is owned by Josh and Remy. Sharath's lane covers integration sync points only.

Operational Impact

How TP Rules Affect Daily Operations

List Creation Workflow
Step 1: Build the list in US Workspace (Database → People Lists or Account Lists).
Step 2: Duplicate to Global Workspace using the Duplicate function.
Step 3: Remove Copy of — prefix and prepend [US] to the list name in Global.
Step 4: Verify geo filter is set to United States (not North America) in both workspaces.
Step 5: If the list feeds an advertising campaign, ensure it's configured in Global Workspace with Person List attached.
Common Pitfalls
• Building in Global first: Violates TP Rule #1. US Workspace is always the source of truth.
• Using "North America" geo filter: Includes Mexico by default, violating data governance.
• Forgetting Person List in ad campaigns: Campaign will fail to target known contacts (TP Rule #4).
• Using Static lists instead of Dynamic: Lists go stale and won't sync from SFDC (TP Rule #5).
• Adding keywords without approval: All keyword changes must route through Sharath (TP Rule #6).
